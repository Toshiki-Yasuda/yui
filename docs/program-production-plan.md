# 「結」配布プログラム 制作実行計画

更新：2026年9月15日。状態：**制作・PDF検証完了。実物の試し刷りは未実施。** 最終仕様と印刷手順は[制作・印刷メモ](program-production.md)を参照。制作中の承認により安田愛のプロフィールは提示された3段落の全文を掲載。印刷用途のため、画面サイズ別の追加検証は対象外。

## 1. 目的と優先順位

来場者が落ち着いて演奏を楽しみ、曲目紹介を読み、終演後も手元で振り返れるプログラムにする。細部の整った文字組みと水彩の統一感で、安心感・高級感を演出する。満足度への効果は制作意図であり、測定済みの成果とは扱わない。

判断の優先順位：

1. **曲目紹介の全文・意味・曲順を守る。省略・要約・生成文への置換をしない。**
2. 客席で曲を探しやすく、長文を無理なく読めること。
3. サイト・既存三つ折り冊子と色、書体、水彩の世界観をそろえること。
4. 余白、罫線、曲番号、字間などの細部を仕上げること。
5. 再生成・検証の簡単さと実行トークンの節約。

装飾のために本文を縮小・削除しない。品質に必要な確認を省く代わりに、再調査・重複作業・大量の別案生成を減らす。

## 2. 確定事項と原本

### 2.1 形式

- A3横1枚を中央で二つ折り。仕上がりA4縦、4ページ。
- 読書順：1 表紙 → 2 第1部 → 3 第2部 → 4 裏表紙。
- 印刷面付け：外面 **4｜1**、中面 **2｜3**。
- 曲目紹介は第1部5曲、第2部6曲。サイトの予告「全12曲程度」を当日プログラムの曲数として転記しない。
- 新規制作物として扱う。既存サイト、チラシ、三つ折り冊子を作り替えない。

### 2.2 使用する資料

| 用途 | 原本／保存先 | 扱い |
|---|---|---|
| 曲目・全文・略歴・主催等 | `プログラム/午後コン　配布プログラムv2.pdf` | 内容の一次原稿。元PDFを保全。実際のファイル名には結合文字があるため、ファイル探索で解決する |
| 指定の3人の水彩画 | `プログラム/reference/ensemble-source.png` | ユーザー添付の元画像をコピー済み。1390×1138px |
| 承認された二つ折りラフ | `プログラム/reference/approved-bifold-direction.png` | 雰囲気・構成の参考限定。画像内の文章、人名、作曲者、略歴を原稿として使わない |
| 配色とWeb上の見せ方 | `css/style.css`、`docs/redesign-review.md` | 色と世界観を参照 |
| 印刷版の表現・既存の知見 | `css/pamphlet.css`、`docs/pamphlet-production.md` | mm/pt設計、PDF生成方法を参照 |

指定画像は一時フォルダから制作フォルダへ保全済み。承認ラフも同様。次の実行で再取得・再生成する必要はない。

### 2.3 内容を扱うルール

- 曲目紹介の曲名、作曲者・編曲者、全本文、曲順、部の区切りを曲単位で保存する。
- PDF抽出による折り返し改行だけを整理する。原稿中の段落、語句、句読点、英字の大小を勝手に変更しない。
- 旧PDFでは表紙テキストが曲目抽出に割り込み、プロフィールに部首文字「土⽥ 祐⽣」が含まれる。全文への一律NFKC変換をしない。抽出誤りの修復は元の見た目と照合し、変更対応表を残す。
- 事実関係や表記に疑問があっても、デザイン変更と一緒に黙って修正しない。必要な点だけ確認メモに分離し、組版は原文で続行する。
- 日時・会場・出演者・休憩・主催後援の情報は原PDFを採用する。別資料との差がある場合だけ差分を記録する。
- ラフで足された詩的なコピー、学歴、出身地、作編曲者などを採用しない。追加文が必要なら既存の確定コピーを使う。
- 販売案内やQRの追加は初期範囲に含めない。来場済みの読者に必要な情報を優先する。

第2部の片段は、幅86.5mm・10.5pt・行間1.55で本文だけ約230mmになる概算。見出し等を含むと250〜265mm程度となりうる。上の少し広い段幅と抑えた見出し高で、実測する。11pt・広い行間を最初から固定しない。

**収まりの調整順**：不要な装飾と余分な見出し高 → 曲名とクレジットの改行 → 段間・余白の許容範囲 → 行送りの許容範囲。文章の削除、横方向の圧縮、文字の隠蔽、極端なマイナス字間は使わない。

2回の実寸調整でも全文・10.5pt下限・4ページが両立しない場合は、問題箇所と実測値を示して構成変更を相談する。黙って8ページ化したり、裏表紙へ解説を移したりしない。これは現時点の確定ブロッカーではなく、収まり検証後の分岐。

## 4. 安心感・高級感の具体的な仕上げ

### 4.1 配色と書体

- 紙面：`#FAF7F2`、本文：`#33302C`、補助：`#57514C`。
- 見出し・表紙の「結」：`#874D57`。文字用ゴールド：`#84642B`。
- 罫線：既存の`#D9CFC3`を基本に、金やローズを限定して使う。
- 色は既存サイトのトークン値を印刷用に対応付ける。Webのpxサイズや影・動きは印刷に持ち込まない。
- 明朝はタイトルと曲目解説、ゴシックは日時・クレジット等の案内に使用。初期は2書体・3ウェイト程度に限定する。
- 真の金属光沢ではなく、印刷色としての落ち着いたゴールド。箔加工は前提にしない。

### 4.2 中面

- 背景に人物、水彩の濃淡、糸、紙の強いテクスチャを敷かない。本文の濃さは全曲一定。
- 段の境界は余白を基本にする。罫を使う場合は0.25〜0.4pt程度で、視線を遮らない。
- 曲見出しと本文最初の2行以上を同じ段に置く。見出しだけの孤立、段頭の句読点、閉じ括弧、極端な1文字行をなくす。
- 原則として1曲を段の途中で分割しない。今回の左1〜3／右4以降の配分で検証する。
- 「結」を最後に読み終える流れを守る。囲み、抜き出しコピー、巨大な番号で読書順を乱さない。
- 休憩は既存の文面を使用し、曲名と混同しない小さな区切りを付ける。

### 4.3 表紙・裏表紙の画像と装飾

- 指定画像の3人の顔、演奏姿、主要な楽器が分かる状態を維持する。まず元画像をそのまま配置する。
- 四角い境界が目立つ場合は、周囲の余白・背景色・対応するマスク表現で調整する。人物を変えずに済む処理を優先する。
- 原画像の編集・再生成が必要な場合はimagegenを使用し、元画像の隣に派生物として保存する。3人の顔・手・マレット・鍵盤・楽器を原画像と比較する。生成による顔の変化を高画質化として黙認しない。
- 指定画像を横180〜184mmで使うと約192〜196ppi。300ppiを満たしたとは扱わない。まず実寸と拡大で検査し、問題が見える場合だけ高解像度原本の有無を確認する。単なる拡大で情報量が増えたとは説明しない。
- 裏表紙の人物カットは、既存画像または指定画像の人物部分から顔が分かる小さなサイズで統一する。3人の顔の見かけの大きさ、氏名の基準線、楽器表記をそろえる。
- 糸は0.3〜0.5ptを目安に、表紙と裏表紙で合わせて2〜3本の穏やかな曲線。音符の大きな装飾、花枠、全面金色は使わない。
- 表紙は水彩画そのものの温かさを中心にし、文字や装飾を増やして高級感を作ろうとしない。

## 5. 原稿・実装・成果物

### 5.1 ファイル構成

必要なファイルだけ新設する。以下は実行時の作成予定であり、現時点で存在するのは本計画と参照資料のみ。

| パス | 役割 |
|---|---|
| `プログラム/source/program.json` | 目視照合済みの全文。部、曲ID、曲名、作編曲者、段落配列、プロフィール、公演情報を保存する編集原本 |
| `プログラム/source/extraction-notes.md` | 原PDFとの対応、抽出時の修復、未解決の表記差だけを記録 |
| `program.html` | 4ページの閲覧用HTML兼PDF原稿。JSONから生成し、本文を二重編集しない |
| `css/program.css` | プログラム専用の画面・印刷スタイル |
| `scripts/prepare-program-assets.py` | 原稿から専用フォントを作る。既存の冊子フォントを上書きしない |
| `scripts/build-program.py` | JSONからHTMLを作り、PDF生成・面付け・検査用の配置情報を出す |
| `scripts/check-program.py` | 原稿一致、寸法、ページ順、フォント、はみ出し等の検査 |
| `scripts/program-requirements.txt` | 実際に動作確認した必要依存のみを固定 |
| `images/program/` | 表紙画像、必要な人物カット、装飾などの使用素材 |
| `fonts/program/` | 全原稿の文字を収録した印刷用フォントとOFLライセンス |
| `docs/program-production.md` | 実行コマンド、最終寸法、印刷手順、検証結果、未確認事項 |
| `tmp/pdfs/program/` | ラスタライズ画像、配置レポート、差分、キャッシュなどの中間データ |

閲覧用HTMLはJavaScriptなしで読める構成を優先。画面の紙面縮小はCSSで簡潔に実装し、必要性が生じたときだけ小さなJSを追加する。

### 5.2 納品PDF

| ファイル | 仕様・用途 |
|---|---|
| `output/pdf/yui-program-a4.pdf` | A4縦210×297mm・4ページ・読書順1,2,3,4。確認・閲覧用 |
| `output/pdf/yui-program-a3.pdf` | A3横420×297mm・2ページ・外面4｜1／中面2｜3。二つ折り印刷用 |
| `output/pdf/yui-program-a3-bleed.pdf` | 426×303mm・2ページ・外周3mm塗り足し。業者の仕様と照合する候補原稿 |

読書順の4ページは一度だけ組版し、同じページ内容を面付けする。内部マスターは1ページ216×303mm（A4の四辺に3mm）として作り、そこから仕上がり210×297mmのページを取り出す。A3原寸版には仕上がりページを並べ、塗り足し版にはマスターの外周部分も利用する。折り目側の塗り足しは表示せず、隣のページへの重なりを防ぐ。本文までクリップしない。

塗り足しはシート外周に設け、折り目に二重の空白や塗り足し帯を作らない。背景・画像の端は必要範囲まで延ばす。A4原寸PDFを後から拡大して塗り足しを作る方法は、文字サイズと余白が変わるため使わない。

塗り足し版のMediaBox/BleedBoxは426×303mm、TrimBoxは左下(3,3)mmから右上(423,300)mm。折り位置は仕上がり左端から210mm、塗り足し版の左端から213mm。トンボは印刷先が要求するときだけ追加する。

PDF内の文字は選択・検索可能なまま保持し、フォントを埋め込む。RGB出力から開始する。PDF/X・CMYK変換・入稿済みとは扱わない。

## 6. 実行順と段階ごとの完了条件

### 段階0：開始状態と依存を確かめる

1. 本計画、適用するスキル、当日の作業ルールを読む。前の会話全体や全素材を再調査しない。
2. `git status --short`を記録する。現在、既存冊子関係などに未コミット変更がある。リセット、包括的なstage、既存変更の巻き戻しをしない。
3. バンドルPythonで専用仮想環境を用意し、必要な依存だけを導入する。既存依存を変更するための大きなリファクタはしない。
4. 当該PDFスキルが要求する制作開始マーカーを、最初のPDF作成・編集に入る直前に一度実行する。計画だけの段階では実行しない。

**事前調査済み**：通常のPythonは3.9.6、バンドルは3.12.14。`.venv-print`と元フォントのキャッシュは存在しなかった。バンドルにpypdf/Pillowはあるが、WeasyPrint/fonttools等が不足。Pango、pdftoppm、pdffonts、pdfinfoは利用できる。実行時は変化の有無を簡潔に確認する。

**完了条件**：使用するPython・依存・レンダラーが確定し、日本語の小さな検証PDFを一度描画できる。

### 段階1：全文原稿を固定する

1. 元PDFを領域／曲単位で抽出し、11曲とプロフィールをJSONへ転記する。
2. 原PDFをページ画像で見ながら、抽出順、冒頭・末尾、句読点、段落、曲名・作編曲者を照合する。
3. 曲ごとのテキストハッシュと元PDFのハッシュを保存する。字数表は補助検査に使う。
4. フォントは新しい全文から専用サブセットを作る。英数字、ページ番号、生成される見出しも含め、全Unicode文字をcmapで確認する。

**完了条件**：11曲の全文と順序が固定され、出典不明の生成文・未解決の転記欠落がない。

### 段階2：最も厳しい第2部を先に組む

1. 表紙の装飾に入る前に、第2部だけを初期寸法でPDF化する。
2. 全文の一致、段末、最後の「結」、見出しの行数、実寸での文字の濃さを確認する。
3. 本文10.5ptと11ptを必要な範囲で比較する。比較案は最大2つから始める。
4. 収まりの調整順に従って寸法を確定する。成立した本文設定を第1部にも使用する。

**完了条件**：本文を削らず、第2部が1ページに収まり、文字の隠蔽・重なり・極端な詰めがない。成立しない場合は構成変更の相談材料をここで作る。

### 段階3：第1部・表紙・裏表紙を仕上げる

1. 第1部に同じ文字組みを適用し、休憩案内を置く。
2. 指定画像を表紙に配置し、3人が見えることと実効解像度を確認する。
3. 裏表紙のプロフィールを原稿から組み、3人の扱いと情報の整列を確認する。
4. 罫線、曲番号、糸、水彩の境界、日付の数字、改行、句読点のぶら下がりを整える。

**完了条件**：全4ページの表現がそろい、中面の読書性が装飾によって損なわれていない。

### 段階4：3種のPDFを出し、まとめて検証する

1. 読書順PDFから2種の面付けPDFを生成する。
2. 自動検査を1セット実行し、全4ページとA3両面のPNGを一度確認する。
3. 独立レビューはこの段階で必要な範囲だけ行う。指摘の修正後は影響した検査とページを中心に再確認する。
4. 最終ソースハッシュ、検証結果、実行コマンドを制作メモに保存する。

**完了条件**：下記の必須検査がすべて通り、最新のPDFの画像を確認済み。失敗・実物未確認は明記する。

### 段階5：提示と試し刷り

- 4ページ一覧、開いた中面、PDFリンクをユーザーへ提示する。
- A3版を原寸100%・両面・短辺綴じを初期設定として試す手順を記す。プリンターによる反転設定の差は、外面4｜1／中面2｜3の向きで確認する。
- 実物では客席を想定した明るさ、反射、裏写り、折りやすさ、3人の顔の画質を確認する。紙の選定や発注は印刷先・実物見本に依存するため、この段階のデジタル検証で済んだとはしない。
- 公開、印刷発注、入稿、コミット／pushは今回の計画作成とは別の操作。制作実行では成果物の作成と提示までを基本範囲とする。

## 7. 必須の品質確認

| 検査 | 合格条件 |
|---|---|
| 全文保存 | 元PDF→確認済みJSON→HTML→読書順PDFを曲IDで照合。11曲の本文が100%一致。空白等の許容差は明示したものだけ |
| 曲順・固有名詞 | 第1部5曲、第2部6曲、曲名・作編曲者・出演者名の誤りなし。生成ラフとの照合はしない |
| レイアウト | 本文10.5pt以上。段・ページ外への文字はみ出しなし。本文をoverflow:hiddenやクリップで隠さない |
| 紙面の余白 | 設計した本文余白を維持し、全文字が断裁・折りから最低5mm以上。5mmを本文の目標余白にはしない |
| フォント | 原稿に使う全文字が収録され、PDFへ埋込済み。豆腐文字、代替フォントの不揃いなし |
| 寸法・面付け | A4 4p、A3 2p、塗り足し2p。寸法誤差0.1mm以内。外面4｜1／中面2｜3、回転・鏡像なし |
| 塗り足し | 正しいTrimBox/BleedBox。画像・背景が外周まで伸び、中央折り目に余計な帯がない |
| 画像 | 表紙で3人の顔と演奏姿を保持。各画像の実効ppiを記録。原寸と拡大で目立つ劣化がないか評価し、解像度不足を数字だけで隠さない |
| 読みやすさ | 本文と背景の画面上コントラスト4.5:1以上を目安に確認。実物の読みやすさは別途試し刷り事項 |
| 生成の新しさ | JSON、テンプレート／ビルドコード、CSS、使用画像、フォントを含む原稿ハッシュがPDFと一致 |
| HTML閲覧 | 1440px程度と390px程度で紙面確認・ダウンロードが機能。変更と無関係なサイト全機能の再試験はしない |
| 変更範囲 | 今回の追加ファイルと意図した差分だけ。既存サイト・チラシ・三つ折り成果物への意図しない変更なし |

文面検査は単に「重要な単語が含まれる」だけにしない。曲ごとの全文と順番を検査する。PDFの抽出順が段組みで交錯する場合は、該当ページ・段の領域で抽出して照合し、誤検出と内容欠落を区別する。

## 8. 必要なときだけ行うエージェント分担

### 8.1 今回の計画段階で完了した分担

- 主担当：目的、紙面構成、装飾方針、受入基準、実行計画の統合。
- 原稿調査担当：11曲の字数、段配分、PDF抽出時の注意を読み取り調査。結果は本計画へ反映済み。
- 印刷基盤担当：既存スクリプトの再利用性、依存、フォント、面付けを読み取り調査。結果は本計画へ反映済み。

これらの調査を実行時に別エージェントへ再依頼しない。ファイルや仕様が変わった場合だけ差分を確認する。

### 8.2 制作時の基本体制

**主担当1名を基本に、独立した仕事が並行できる場合だけ補助を起動する。** 全員のモデルは現在の設定を継承する。存在しないモデル名や、別製品のOpus/Sonnet/Haikuという区分をそのまま指定しない。役割と推論の必要性で仕事を分け、品質判断は主担当が引き受ける。

| 役割 | 任せる仕事 | 起動条件・境界 |
|---|---|---|
| 主担当／編集・デザイン責任者 | 原稿固定、第2部の試し組み、全体デザイン、画像選定、統合、最終判断 | 常時。目的やデザイン方針の判断を複数エージェントに重複させない |
| PDF実装担当 | 面付け、ページボックス、ハッシュ、検査処理の実装 | 主担当が本文・表紙を作業中で、4ページのHTML構造と入出力仕様を固定できた場合のみ。担当は`build-program.py`／`check-program.py`等に限定 |
| 原稿照合または組版レビュー担当 | 全文差分、人物の欠け、孤立見出し、段末、面付けなどを独立に確認 | 最初の完成候補ができた後。数値検査だけでは拾えない品質判断が必要な場合のみ。読み取り専用、勝手に原稿を直さない |

通常は主担当＋補助1名まで。同時に最大2補助を使うのは、ファイルの所有範囲が衝突せず、独立に進む理由がある場合だけ。単純な抽出・検索・PDF画像化はまず通常のツールでまとめて実行する。

### 8.3 依頼するときの短い契約

毎回、以下だけを渡す。会話全文・全資料・長い経緯を重複して渡さない。

1. 目的と完了条件。
2. 読むファイルと担当ファイル。
3. 確定仕様と触ってはいけない箇所。
4. 依存する入力の状態とインターフェース。
5. 必要な検査と、結果の返し方。

実装担当への例：

> 本計画のPDF仕様に従い、塗り足しを含む216×303mm・読書順4ページの内部マスターから、A4原寸版、A3外面4｜1／中面2｜3、A3塗り足し版を作る処理を実装する。担当は指定したscripts配下だけ。JSONの文言、HTML構成、CSS、既存冊子のファイルは変更しない。寸法・面順・ハッシュ・文字抽出を検証し、変更ファイル、結果、未解決点を短く報告する。新しいエージェントは起動しない。

レビュー担当への例：

> 原PDF、固定JSON、今回のPDFと検査用PNGだけを読み、全文欠落・誤表記・組版・画像・面付けの問題を確認する。書き換えない。指摘は「ページ／曲・場所／問題／根拠／最小修正案」の形で最大5件。好みの別案は不要。問題がなければ確認した範囲を報告する。

主担当は成果を確認して統合する。同じファイルを複数人が編集しない。並列化のためだけにworktreeを作らない。エージェントの報告待ちの間にも、主担当は独立した作業を進める。

## 9. トークンと手戻りを減らす運用

- 最初に本計画を読む。既に確定した形式・画像・全文保持について繰り返し質問しない。
